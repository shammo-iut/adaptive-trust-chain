## Overview

This repository contains the open-source executable specification for the **Adaptive Trust Chain (ATC)** — a five-layer permissioned-blockchain architecture for weld-parameter compliance in green hydrogen infrastructure. The central contribution is linking in-process weld-parameter capture, cryptographic NDT binding, and a PLC-level production-enabling Compliance Bit in one auditable chain.

## The Adaptive Smart Contract (`WeldComplianceASC.sol`)

The Solidity contract implements **Algorithm 1** (`checkCompliance`) from the paper. It evaluates five pre-weld conditions sequentially:

1. Welder DID registered in `welderRegistry`
2. ISO 9606-1 certificate not expired (`block.timestamp ≤ expiry`)
3. Equipment calibration current (`calibrationRegistry[equipmentID]`)
4. Pre-heat temperature ≥ `thresholds.minPreheat` (ISO 15614-1)
5. Inter-pass temperature ≤ `thresholds.maxInterpass` + humidity ≤ `thresholds.maxHumidity` (EN 1011-2)

**The "adaptive" threshold update mechanism** (why the contract is called "Adaptive"):

```solidity
// Any council member proposes; ≥ 2/3 must approve before execution
function proposeThresholdUpdate(string calldata param, uint256 proposedValue)
    external onlyCouncil returns (uint256 proposalID)

function approveProposal(uint256 proposalID) external onlyCouncil
```

Thresholds update automatically when ≥ 2/3 of the governance council approve — e.g. when a WPS is re-qualified or ISO 3834 / EN 13445 / the EU Hydrogen Package is revised. Every update emits a `ThresholdUpdated` event with old value, new value, and approving address, creating an on-chain audit trail.

**⚠️ Design limitation (paper Section 4.3, 4.5):** The single global `thresholds` object is for expository clarity. A production deployment must resolve `thresholds[WPS_ID]` per the applicable qualified Welding Procedure Specification / Procedure Qualification Record. The contract is an executable specification; it has not been deployed, formally verified, or externally audited.

## The ASI-PLC State Machine (`Prototype.py`)

Implements **Algorithm 2** from the paper — the five-step Compliance Bit decision cycle running on a 500 ms heartbeat aligned with QBFT finality:

```
Step 1 — Heartbeat check      latency > 500 ms          → SOFT_LOCK
Step 2 — Anti-replay nonce    nonce ≤ lastNonce          → HARD_LOCK
Step 3 — HMAC-SHA256 verify   signature mismatch         → HARD_LOCK
Step 4 — Asymmetric verify    Oracle identity invalid    → HARD_LOCK
Step 5 — Compliance Bit       all checks pass            → COMPLIANT / NON_COMPLIANT
```

**Emergency-stop polarity convention (paper Section 4.4):**

```
EStop_OK = TRUE   → E-stop circuit is healthy (NOT active)
EStop_OK = FALSE  → E-stop has been triggered
WeldingRelay = ComplianceBit AND EStop_OK
```

This is stated explicitly rather than left implicit to avoid the active-high/active-low ambiguity discussed in Section 4.4.

**PLC States:**

| State | Relay | Recovery |
|---|---|---|
| `COMPLIANT` | ON | — |
| `NON_COMPLIANT` | OFF | Automatic on next compliant cycle |
| `SOFT_LOCK` | OFF | Automatic on heartbeat restoration |
| `HARD_LOCK` | OFF | **Manual admin reset only** |

## Monte Carlo Results (n=200, seed=2025)

Running `python Prototype.py` reproduces all results reported in **Section 7** of the paper:

| Metric | Value |
|---|---|
| Valid scenario mean latency | **274.0 ms** |
| Valid scenario P95 latency | **320.0 ms** |
| Timeout boundary case | **486.2 ms** → HARD_LOCK (HardLock persisting from prior attacks) |
| False positives (non-valid → relay ON) | **0** |
| False negatives (valid → relay OFF) | **0** |
| Timeout SOFT_LOCK / HARD_LOCK | **9 / 1** |

**Why one timeout resolves as HARD_LOCK, not SOFT_LOCK:**
The third timeout draw (486.2 ms) falls below the 500 ms heartbeat threshold, so Step 1 does not fire. Steps 2–4 pass. At Step 6, `HardLock = TRUE` (persisting from the preceding MitM/Replay attack scenarios, no admin reset between groups) suppresses `ComplianceBit`. The relay stays OFF via HARD_LOCK rather than SOFT_LOCK. This is the scenario described in Section 7 of the paper.

### Scenario plan

| Scenario | n | Fault type | Expected outcome |
|---|---|---|---|
| Valid (compliant) | 120 | `NONE` | COMPLIANT — relay ON |
| Non-compliant weld | 50 | `NON_COMPLY` | NON_COMPLIANT — relay OFF |
| MitM attack | 10 | `MITM` | HARD_LOCK — relay OFF |
| Replay attack | 10 | `REPLAY` | HARD_LOCK — relay OFF |
| Oracle timeout | 10 | `TIMEOUT` | 9× SOFT_LOCK, 1× HARD_LOCK |

## Security Scenarios Tested

| Threat | Injection method | ATC response |
|---|---|---|
| MitM payload injection | HMAC signature corrupted | HARD_LOCK — manual reset required |
| Replay attack | Stale nonce (nonce=1) | HARD_LOCK — monotonic nonce check fails |
| Oracle connectivity loss | Latency from N(514.6, 20) ms | SOFT_LOCK — relay de-energised, auto-recovers |
| Non-compliant weld | `compliant_flag = False` | NON_COMPLIANT — relay stays off |

These correspond to the STRIDE threat model in Table 3 of the companion paper.

## Limitations

- Latency values are drawn from **assumed normal distributions** based on published QBFT benchmarks (Saleh & Cevik, 2025), not measured on physical hardware.
- The asymmetric signature check (Algorithm 2, Step 4) uses a **hash-based stand-in**, not a live Ed25519 verification; production requires an HSM-backed Oracle key.
- The Solidity contract has **not been deployed, formally verified, or audited**.
- Field performance under industrial electromagnetic and network conditions remains untested.
